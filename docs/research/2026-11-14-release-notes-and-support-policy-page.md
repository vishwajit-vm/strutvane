## Versioning scheme

Every Strutvane package follows [Semantic Versioning](https://semver.org). The framework packages always share one version number:
- `@strutvane/framework`
- `@strutvane/auth`
- `@strutvane/ui`
- `create-strutvane`
- `strutvane`

So "Strutvane 0.2.4" means all of them at `0.2.4`.

**Before 1.0:**
- **New lines** (`0.2 → 0.3`) **may contain breaking changes**, each listed in the [upgrade guide](/docs/{{version}}/upgrade).
- **Releases within a line** (`0.2.3 → 0.2.4`) **never break your app**. They contain bug fixes and backward-compatible features, so updating within a line is always safe.
- A new line ships at most once every three months.

**From 1.0:**
- Strutvane ships **one major release a year** (around Q1). Only majors may break.
- **Minor and patch releases** ship as often as every week and never break.
- Major upgrades should take a day or less.

In your app, always depend on the line you use. `create-strutvane` writes this for you:

```json
"@strutvane/framework": "^0.2.4"
```

Before 1.0, `^0.2.4` means "any 0.2 release from 0.2.4 on", never 0.3. From 1.0, `^1.4.0` means "any 1.x".

### What counts as public API

Strutvane's compatibility promise covers:
- everything a package exports;
- `node strut` commands and flags;
- installer prompts and flags;
- config files and `.env` keys;
- the migration Schema builder;
- the shape of generated files (`.strutvane/*`, `resources.json`, `ui.gen.ts`);
- the HTTP conventions of the generated API (query parameters, error `code`s, the pagination envelope);
- the tables the framework owns.

Code we generate into your app counts too. If a release would make an app generated by an earlier release of the same line stop compiling or behave differently, that's a bug.

**Not covered** (these may change in any release):
- imports from `internal` paths, or anything marked `@internal`;
- the wording of log lines, error `detail` text and human-readable CLI output (use `--json` for scripts);
- the exact SQL the ORM generates;
- the order of keys in generated JSON;
- the HTML of developer pages under `/_strutvane/`.

> Note: this mirrors Laravel's "named arguments are not covered" paragraph. Keep the list short and concrete.

## Support policy

**Before 1.0:**
- The **newest** 0.x line gets bug fixes and security fixes.
- When the next line ships, the previous one gets **security fixes for 6 more months**, then reaches end of life.

**From 1.0:** every major gets **bug fixes for 18 months** and **security fixes for 2 years** from its release.

**Add-on packages** (`@strutvane/log-viewer`, `@strutvane/files`, …):
- Before 1.0 they share the framework's version and its support window.
- From 1.0 they have their own versions, and only their latest major gets fixes.

**What a "bug fix" and a "security fix" are:**
- A **security fix** fixes a vulnerability published as a GitHub Security Advisory.
- A **bug fix** fixes anything that doesn't work as these docs describe.
- In a security-only line, we may also fix critical bugs, such as data loss or a broken upgrade path, but we don't promise to.

## Which version should I use?

- **New project:** `npm create strutvane@latest my-app`. You get the current line.
- **Existing project:** stay on your line and update freely within it (`npm update`). Before your line's bug-fix window ends, follow the [upgrade guide](/docs/{{version}}/upgrade) to the next line.
- **`node strut about`** prints your version and its support status.
- **`node strut doctor`** warns when your line is security-only or end of life.

## Installing an older version

Every line stays installable. Its documentation stays online at `/docs/<line>/`, with the version switcher in the header.

```bash
npm create strutvane@0.2 my-app          # the newest 0.2 starter → a 0.2 app
npm install @strutvane/framework@latest-0.2   # the newest release of an older maintained line
npm create strutvane@next my-app         # a preview of the next line (not for production)
```

npm dist-tags:

| Tag | Meaning |
|---|---|
| `latest` | the current line |
| `latest-0.2`, `latest-1`, … | the newest release of an older line that is still maintained |
| `next` | previews of the next line, built from `main` |

The starter refuses to create an app on an end-of-life line unless you pass `--allow-eol`.

## Deprecations

Before anything is removed, it's deprecated for at least one full line:
- Your editor shows it struck through, with the replacement (TSDoc `@deprecated`).
- At runtime, Strutvane logs a warning once per process. The warning has a stable code like `STRUTVANE_DEPRECATED_…` and tells you what to use instead.
- Set `STRUTVANE_DEPRECATIONS=throw` in your tests to turn the warnings into errors, or `off` to silence them.
- `node strut doctor` lists deprecated config keys and flags your app still uses.
- The [Deprecations page](/docs/{{version}}/deprecations) lists everything deprecated in this line and when it will be removed.

Removal happens only in a new breaking line: the next 0.x line before 1.0, the next major from 1.0. Renamed APIs keep the old name as an alias for a full line. The only exception is a security fix, which may change behaviour immediately. It's always announced, with an entry in the upgrade guide.

## Security

**Please don't report security problems in public issues.** Use GitHub's private vulnerability reporting on the [Strutvane repository](https://github.com/vishwajit-vm/strutvane/security). See `SECURITY.md` for the email fallback.

When we fix a vulnerability:
- we release every affected line that still gets security fixes **on the same day**;
- we publish a GitHub Security Advisory listing the fixed version for each line;
- `npm audit` reports it to you.

End-of-life lines don't get fixes: the advisory tells you which line to upgrade to.

Every release is built in CI with npm provenance and approved by a maintainer with two-factor authentication before it goes live.
