# 16 — Documentation & Long-term Ecosystem Strategy

## Part A — Public documentation

### A.1 Structure (Diátaxis)

The docs site lives at `strutvane.dev` and is built from the `strutvane/docs` repo.

```
Getting started
  ├─ What is Strutvane? (5-minute read)
  ├─ Installation (presets: full / api / ui)
  └─ Tutorial: Build a B2B app in 2 hours (CRM: companies, contacts, deals, auth, roles, UI)
Tutorials (learning-oriented)
  ├─ Your first API in 15 minutes
  ├─ Adding auth and roles
  ├─ Multi-tenant SaaS from day one
  └─ Connecting the UI to an existing API
How-to guides (task-oriented)
  ├─ Models: fields, relations, enums, JSON, money, soft deletes, versioning
  ├─ Migrations: auto, manual, zero-downtime, per-tenant, brownfield (db:pull)
  ├─ API: filters, custom actions, custom routes, versioning, rate limits, exports
  ├─ Auth: providers, SSO (Entra ID/Okta), SCIM, MFA, API keys, impersonation
  ├─ UI: themes, layouts, custom widgets, page overrides, eject
  ├─ Databases: Azure PostgreSQL (passwordless), Azure MySQL, Neon, Supabase, RDS
  ├─ Jobs, schedules, cache, mail, events, webhooks
  ├─ Testing your app
  └─ Deploying: Azure Container Apps, AWS ECS, Fly.io, Railway, Kubernetes
Reference (information-oriented, mostly generated)
  ├─ CLI (generated from command definitions)
  ├─ Config (generated from config schemas)
  ├─ Field types & modifiers
  ├─ HTTP list query protocol, errors (problem+json codes)
  ├─ Contracts (TypeDoc from @strutvane/contracts)
  └─ Package APIs (TypeDoc per package)
Explanation (understanding-oriented)
  ├─ Architecture & request lifecycle
  ├─ Levels of control (L0–L3)
  ├─ Authorization model & tenancy isolation
  ├─ Security model
  └─ Comparisons: vs Laravel, NestJS, AdonisJS, Payload, Refine, React Admin
Ecosystem
  ├─ Packages (first-party) · Plugins (community) · Writing a plugin/installer/generator
Upgrade guides · Changelog · Roadmap · RFCs · Security policy
```

### A.2 Docs engineering

| Topic | Approach |
|-------|----------|
| Tooling | Astro Starlight (or VitePress). Decide in Phase 0; verify current versions then. |
| Versioning | Docs versioned per major. "Edit this page" on every page. |
| Reference content | Generated from source: CLI help, config JSON Schema, TypeDoc |
| Code samples | Type-checked in CI (extracted and compiled against the current packages) |
| Tutorial validation | Tutorials are executed by CI end-to-end (a scripted run of every command in the tutorial) |
| Search | Pagefind (static) |
| Machine-readable docs | `llms.txt` and `llms-full.txt` published for AI coding assistants |
| AI assistant support | An MCP server (`@strutvane/mcp`, post-1.0) exposing models, routes and permissions of a project to coding agents |
| Definition of done | A feature PR includes docs + an example + tests, or it does not merge |

## Part B — Long-term ecosystem strategy

### B.1 Growth model

```
Year 1: framework + auth + ui  →  "fastest way to a real B2B app in TypeScript"
Year 2: notify, files, logs, reports, payments/billing, analytics  →  "everything a SaaS needs"
Year 3: marketplace, visual studio, Vue renderer, serverless/edge mode, certified partners
```

**Every new first-party package MUST:**

1. Be installable standalone and implement the **installer protocol** (config, env keys in `.env` + `.env.example`, migrations, routes, UI pieces when ui is present).
2. Depend only on `core` + `contracts`, and enhance other packages via `enhances`.
3. Ship L0–L3 levels of control where it generates code.
4. Pass the shared security, testing and docs bars.
5. Go through an RFC that includes a "why not a plugin?" section.

### B.2 Governance

- **Licence:** MIT, permanently. Enterprise capabilities (RBAC, audit, tenancy, SSO, SCIM) are never moved behind a paid licence. This is written into `GOVERNANCE.md`.
- **Contributions:** DCO sign-off, not a relicensing CLA.
- **Decisions:** RFCs for public API/contracts changes. ADRs for internal decisions. A core team with documented roles. A path from contributor to maintainer.
- **Security:** SECURITY.md, private advisories (GHSA), coordinated disclosure, an SLA (acknowledge in 48 h, fix highs in ≤ 14 days).
- **Neutrality:** consider moving to a foundation (e.g. OpenJS Foundation) once adoption justifies it. This protects users from the pivot and relicensing pattern seen across the category.

### B.3 Sustainability (no licence games)

| Stream | Notes |
|--------|-------|
| GitHub Sponsors / Open Collective | From day one; transparent spending |
| Corporate sponsorship tiers | Logo on site/README; no roadmap control |
| Paid support & SLAs | For enterprises adopting Strutvane |
| Training & certification | Courses, workshops, "Strutvane Certified Developer" |
| Premium starter kits / themes (optional) | Separately licensed *content*, never core capabilities |
| Hosted add-ons (optional, later) | e.g. managed audit-log archive or error tracking. Strictly optional; everything self-hostable. |

### B.4 Community

- Discord + GitHub Discussions.
- "Good first issue" pipeline.
- Monthly release notes and quarterly roadmap updates.
- Showcase of apps built with Strutvane.
- Plugin authoring guide + `sv plugin:create` scaffold + plugin directory on the docs site.
- Starter kits for common B2B domains: CRM, helpdesk, inventory, HR, booking, invoicing.
