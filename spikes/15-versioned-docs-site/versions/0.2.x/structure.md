## The big picture

A new Strutvane app uses Laravel's layout, so if you've seen a Laravel project you'll feel at home. Here is what `npm create strutvane@latest my-app` gives you:

```text
my-app/
├─ app/
│  ├─ http/
│  │  ├─ controllers/      your controllers (optional: resources work without one)
│  │  ├─ middleware/       code that runs before or after requests
│  │  └─ requests/         form requests (validation rules)
│  ├─ models/              one class per table: post.ts, user.ts
│  ├─ policies/            who may do what: post-policy.ts
│  └─ providers/           register your own services
├─ bootstrap/
│  ├─ app.ts               builds the application: routing, middleware, errors
│  └─ providers.ts         the list of service providers
├─ config/                 typed settings: app.ts, database.ts, auth.ts, …
├─ database/
│  ├─ migrations/          your tables and columns (the source of truth)
│  ├─ seeders/             starting data: database-seeder.ts and one per table
│  └─ factories/           fake records for tests and seeders
├─ resources/
│  └─ ui/                  your UI customisations: posts.ui.ts, pages, components
├─ routes/
│  ├─ web.ts               routes for the browser
│  ├─ api.ts               routes for the JSON API
│  └─ resources.gen.ts     generated: one API resource per model (don't edit)
├─ storage/                files your app writes: uploads, logs
├─ tests/                  your tests
├─ .strutvane/             generated by Strutvane (mostly git-ignored)
├─ .env                    your local settings and secrets (never committed)
├─ .env.example            the list of every setting, without secrets (committed)
├─ package.json
└─ strut.js                the command line: node strut <command>
```

## Folder by folder

### `app/`: your application code

This is where most of your own code goes.

- **`app/models/`** has one class per table. A model holds *behaviour*, not columns: the columns come from your migrations, with their exact names (`created_at`, `author_id`). The only list you write is `fillable`, the columns people may set through forms and the API; anything else is refused (mass-assignment protection):

  ```ts
  // app/models/post.ts
  export class Post extends Model('posts', { fillable: ['title', 'body', 'status'] }) {
    author() {
      return this.belongsTo(User, 'author_id')
    }
  }
  ```

- **`app/policies/`** decides who may do what. `post-policy.ts` is found automatically because of its name. With no policy, the answer is **no** (deny by default).
- **`app/http/controllers/`** is optional. Every table with a model already gets a full API after `node strut migrate`. Write a controller only when you want different behaviour: `node strut make:controller PostController --resource`.
- **`app/http/requests/`** holds form requests: validation rules for your own routes.
- **`app/http/middleware/`** and **`app/providers/`** are for code that runs around requests and for registering your own services.

### `bootstrap/`: how the app starts

`bootstrap/app.ts` builds your application in one readable chain (routing, middleware, error handling), just like Laravel's `bootstrap/app.php`. `bootstrap/providers.ts` lists the service providers; installing a package adds its line here for you.

### `config/`: settings

Typed settings files that read `.env`. See [Configuration](../configuration/).

### `database/`: tables and data

- **`migrations/`** is the **source of truth** for your tables. Columns are written here, and only here. See [Migrations](../migrations/).
- **`seeders/`** fills the database with starting data. `database-seeder.ts` runs the others in the right order. See [Seeding](../seeding/).
- **`factories/`** makes realistic fake records for tests and seeders.

### `resources/ui/`: your screens

The generated admin screens are driven by small files you own. The first time a table appears, `node strut migrate` writes `resources/ui/posts.ui.ts` with `columns: auto()` and `form: auto()`. Change it as you like: Strutvane **never overwrites it**. Custom pages and components live here too.

### `routes/`

`routes/web.ts` and `routes/api.ts` are yours. `routes/resources.gen.ts` is **written by Strutvane** on every migrate: it registers one API resource per model, and `routes/api.ts` imports it. Don't edit it; to change one resource, write your own controller.

### `.strutvane/`: generated files

`node strut migrate` writes here: the TypeScript types for your tables (`.strutvane/types/models.d.ts`), the metadata the API and UI run on (`.strutvane/resources.json`) and the generated UI registry (`.strutvane/ui.gen.ts`). It's regenerated every time, so you never edit it, and most of it is git-ignored.

### `strut.js`: the command line

`node strut <command>` is Strutvane's `php artisan`. Run `node strut help` to see every command.

### `docker/` (only if you chose Docker)

If the installer runs your database in Docker, it writes `docker/compose.yaml`. It's for your machine only and is git-ignored; `npm run setup` recreates it for teammates.

## Who writes which file?

| File | Written by | Overwritten later? |
|---|---|---|
| `database/migrations/*.ts` | `make:migration`, then you | Never |
| `app/models/post.ts` | `make:migration` (first time), then you | Never |
| `resources/ui/posts.ui.ts` | `migrate` (first time), then you | Never |
| `routes/resources.gen.ts` | `migrate` | Every migrate |
| `.strutvane/**` | `migrate` | Every migrate |

The rule is simple: **files you own are never overwritten**. Generated files say so in their name (`.gen.ts`) or live in `.strutvane/`.
